# Plan v3

Builds on [Plan v2](2026-11-09-plan-v2.md). Adds: a one-line Compass, quarter tabs (goals of later quarters), products per block, and
habits linked to goals. No personal data lives in this repo; examples use generic blocks ("Studio", "Fitness").

## What changes for the owner

- **Compass** is one line, `COMPASS · <first sentence of the mission>`, with `Mission & vision` (opens both texts side by side in small
  type, max 62 characters wide) and `Edit`. Open or closed is kept in `localStorage` (`niyyah.compass.open`). While the compass loads
  a line-high placeholder holds its place, so the page does not jump.
- **Quarter tabs** sit in the Block column header: the current quarter, the next, any later quarter that has goals, and `+` (opens the
  quarter after the last tab). Labels `Q4'26`, `Q1'27 · next`. The open tab decides which goal lines the block cell shows and where
  `+ <Q> goal` adds. The task goal picker offers goals of the task's block in the current and any later quarter, labelled with the
  quarter; a task nested under a later goal shows `↳ <goal> · Q1'27` in its cell.
- **Products** are named parts of a block, managed inline (`Products` in the block cell): chips with add, rename (✎) and delete (×).
  Delete asks first and says how many tasks and goal lines lose the tag. Goals of the open quarter sit under small product headings
  (the block's product order, then `no product`); `+ goal` lets you pick a product; `Edit goals` has a product picker per line. The
  task side card has product chips (toggle). A `#tag` typed in a task that is not a product stays a plain tag.
- **Habits** (a habit's Plan block is its existing `stream`): under each goal `↻ name · n/wk · wk x/gate` and a mini bar; habits of the
  block with no goal under `habits · no goal`; a habit whose goal's quarter ended stays linked and shows under
  `↳ <goal> · Q4'26 ended` (warning colour) with `re-link` (opens the habit card). At the top of each block's Now cell: this week's ticks
  per habit (one dot per day a week, `n/per_week`, `+1` = today `done` through the existing check endpoint; `✓` undoes today).
  Habits of blocks that are not Plan blocks stay on the Habits board only. Goal focus dims the other goals' habits.
- **Make it a habit** (task side card, with a confirm that names the day block it lands in and what is not kept): one request creates
  the habit and deletes the task; the habit card opens (cadence 3/4/5/7, stage and week, goal picker). Short details (up to 120
  characters) become the habit's `minimum`; longer details, sub-tasks and tags are not kept (the confirm lists them).

## Model

### Table `planner_products` (revision `a2c4e6f8b0d3`, after `f1a3c5e7b9d2`)

`id`, `user_id` FK (cascade), `block VARCHAR(24)` (the stream slug), `slug VARCHAR(32)`, `name VARCHAR(60)`, `position INT` (default 0),
`created_at`; `UNIQUE (user_id, block, slug)`. The same revision adds `planner_habits.goal_ref VARCHAR(16) NULL`. DDL only; the
downgrade drops the table and the column. Verified on Postgres 17 (docker): chain from empty up, old-style habit INSERT still works,
unique key and cascade, down, up.

### Slugs and tags

`slug` = the name lowercased, runs of anything but letters and digits as one dash, at most 32 characters, starting with a letter
(`rules.product_slug_of`; the same function in `lib/plan-v3.ts` `tagSlug`). A task carries a product as a tag in
`planner_tasks.products`; a tag **is** the product when `tag_slug(tag) == slug` (so `#DNS` and `dns` are one product). A task's
products = its tags that are products of its block; other tags stay plain. Setting a task's products replaces only the product tags.

### Goal lines

`goal_checklist` lines may carry `product` (a slug of an existing product of that block). `rules.clean_checklist(..., products, strict)`
keeps it when the slug is in `products`; otherwise drops it (the older `PUT /quarter/stream`) or refuses it (`strict`, used by
`PUT /plan/goals`, a 422). Month checklists never carry one. The shadow item tree projects it into the goal-line item's `tags`
(`planner_items.tags`), so `tree-check` stays equal after a product is set, renamed or deleted (tests).

### Future quarters

Every Plan read and every goal write first runs `plan_v2.carry_streams` for its quarter: **each block of the latest earlier quarter
that the target has no row for is copied** (empty goals and checkpoints), so a block added in Q4 after a Q1 goal was written still
exists on 2027-01-01. Rows the target already has are never touched (a rename in the earlier quarter after the target exists does not
propagate). A quarter row is created **only by a write** (`PUT /plan/goals`): `plan_v2.ensure_block_in_quarter` runs `carry_streams` for that
quarter (v2's carry, parameterised by quarter: copies the latest earlier quarter's blocks with empty goals and checkpoints) and, for a
block that has no row there (created after the quarter), copies that block's latest earlier row. Both inserts run in a savepoint on the
unique `(user, quarter, slug)` index, so concurrent writers end with one set of rows. Reads never create a future quarter. A quarter
before the current one is refused (422).

### Habit goals

A habit's **Plan block** is its `stream` (it already existed: "the goal it serves"); when `stream` is NULL it is the habit's day `block`
if that key is also a Plan block slug of the current quarter (real habits often only have `block`, e.g. `fnf`). Otherwise the habit is
in no Plan block: it stays on the Habits board and linking it to a goal is refused (422). The habits read model returns `plan_block`;
the Plan table (block cell, Now ticks) and the habit card use it. Linking such a habit (API or `plan-v3-migrate`) also sets
`stream` = its Plan block; the CLI journal records that update so a revert restores NULL. `goal_ref` is a goal line of that block in
the current or a later quarter. A habit keeps its `goal_ref` when the quarter ends (the pipelines read names it in `ended_goals`, as for
tasks); re-sending the ref it already has is accepted, a new pick must be current or later. Changing or clearing the habit's `stream`
clears `goal_ref` unless a new one is sent. `GET /vault/habits` returns `goal_ref`.

## API (additive; OpenAPI contract and `core_routes.json` regenerated)

| Endpoint | Purpose |
|---|---|
| `GET /vault/products?block=` | the owner's products, with `tasks` and `goals` counts |
| `POST /vault/products` `{block, name}` | create; slug from the name; same slug in the block → 409 |
| `PUT /vault/products/{id}` `{name}` | rename name **and** slug; rewrites the tag on every `planner_tasks.products` and `planner_event_overlays.products` of that user+block and every goal-line `product` of that block in all quarters, one transaction; slug collision → 409 |
| `DELETE /vault/products/{id}` | removes the tag and the goal-line `product`; keeps tasks and goals; answers `{products, tasks, goals}` (what lost the tag) |
| `PUT /vault/products/reorder` `{block, ids}` | every product of the block once |
| `PUT /vault/plan/goals` `{stream, quarter, goals}` | replace a block's goal lines in a quarter (current or later); creates the quarter row; product validated (422) |
| `PUT /vault/pipeline/products` `{stream, line, products}` | set a task's product tags |
| `POST /vault/pipeline/to-habit` `{stream, line}` | habit (name = task text, day block = the user's first non-archived day block, `stream` = task stream, 3/wk, installing, started today, `goal_ref` = the task's when still valid) + delete the task, one transaction; answers the habits and `habit_id` |
| `GET /vault/pipelines` | each block gains `products` and `quarter_goals` (current + later quarters with a row); top level `quarters` (the tabs: current, next, later ones with goals); `ended_goals` also names the goals habits are linked to |
| `PUT /vault/habits/{id}` | `goal_ref` / `clear_goal`; `POST /vault/habits` takes `goal_ref` |
| `PUT /vault/pipeline/goal` | a goal of the task's block in the current or any later quarter; an existing ref stays accepted |

Product error codes: duplicate slug 409; unknown block/product, bad name, product not in the block 422. Everything is owner-scoped.

### Export / import (docs/export-format.md)

`products` (`block`, `slug`, `name`, `position`) and `habits[].goal_ref`; the goal-line `product` rides inside `goal_checklist`. Import
validates: a goal-line product must be listed in `products` for that block, no duplicate `(block, slug)`; a file without `products`
leaves the account's products alone. Golden export updated.

### Legacy table

`planner_pipeline_items` is read and written by nothing any more (only the import wipe and the migration mapping touch it), so product
rename/delete do not rewrite it. `planner_event_overlays.products` **is** live and is rewritten.

## CLI: `python -m app.cli plan-v3-migrate --user N [--apply] [--journal p] [--habit-goals file.json] [--revert j]`

Dry run unless `--apply`; one line per change; `TOTAL n changes`; last line `SUMMARY products=<n> habit_goals=<n>`. Steps:

1. **Seed products** from the tags in use: for each block, each distinct tag on **all** of the user's `planner_tasks` rows with a stream
   (lane or not) and on `planner_event_overlays` with a stream, in order of first appearance. Slug = the tag made tag-safe, name = the
   tag with dashes as spaces, Title Case, position after the block's last product. Skipped, with a printed reason: a slug the block
   already has, a tag that cannot start a slug (`2fa`), a stream no quarter defines, a block already at 30 products. The dry run prints
   `block=<b> products after: a, b, c` per block.
2. **Habit goals** from `{"<habit id>": "<goal line id>"}`: the habit must exist for the user and have a Plan block (`stream`), and the
   line must be a goal of that block **this quarter**, else the whole run is refused before any write. Set only where `goal_ref` is NULL
   (others are printed and left alone).

Never deletes or edits a task, a tag, a goal line or an existing product. A second run prints `TOTAL 0 changes` and writes no journal.

**Journal** (`plan-v3-migrate-<user>-<UTC>.json` or `--journal`): written before the commit; full-row snapshots of created products and
`(id, column, old, new)` for habits. A failed commit renames it `<name>.uncertain`. **Revert** (`--revert`, dry run unless `--apply`):
a product is deleted only if **every column** still equals its snapshot (renamed, reordered or re-slugged since → skipped and printed)
and no goal line of its block carries it (else the line would hold a stale slug; skipped and printed; task tags are plain tags and do not block);
a `goal_ref` is restored only if it still equals what the run set.

## Rollback order

1. **Data first**: `plan-v3-migrate --revert <journal> --apply` (the old image has no CLI).
2. Then the image: redeploy the previous one; it ignores the new table, the new column and the goal-line `product` key.
3. The old image keeps a goal line's `product` key in the JSON until someone edits that block's goals there (its checklist cleaning
   drops the key); after a rollback run `python -m app.cli tree-rebuild --user N` so the shadow tree's tags follow.
4. The schema revision can stay (additive) or be downgraded after step 2 (`alembic downgrade f1a3c5e7b9d2`: drops `planner_products`
   and `planner_habits.goal_ref`; the products and the habit links are lost, tasks keep their tags).

Tags rewritten by a rename after the seed are not undone by the revert (it skips renamed products); that is by design: the tags are
the owner's data once they have been edited.
