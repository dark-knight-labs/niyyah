# Plan v2

One table replaces the Plan page's "Horizons" map and "Work" list. Blocks are rows, their quarter goals sit in the first
column, tasks sit in Now, Next and Someday. Done is its own view. No personal data lives in this repo; examples use
generic blocks ("Studio", "Fitness").

## Model

- **Block** = the existing quarter stream (`planner_quarter_streams`). **Quarter goals** = its `goal_checklist` lines (stable ids).
  Quarters are shown as `Q4'26`.
- **Task** = a pipeline item (`planner_tasks` with a `lane`). Status: Now (lane `now`, this week), Next (`next`, prioritised,
  ordered by `lane_position`), Someday (`backlog`), Done (`done`).
- **Nesting**: `goal_ref` (VARCHAR(16), NULL) = the id of one goal line of the task's block. NULL = not nested. A goal of an
  ended quarter keeps its tasks; the table shows `↳ <goal> · Q3'26 ended` in the warning colour (the API returns such goals as
  `ended_goals` per block on `GET /vault/pipelines`).
- **Label**: one of `label_month` (`YYYY-MM`, shown `Nov-2026`) or `label_date` (shown `Thu 12 Nov`), or none. Late = month before
  the current month, or day before today, while not done.
- The month checkpoint concept is retired from the Plan UI. `checkpoint` and the checkpoint checklists stay in the data.

### Date label decision: new column `label_date`

`scheduled_on` is **not** safe for a lane item: the undated tray (`planner_items.py`, `scheduled_on IS NULL`) would drop it,
the day/week/calendar views (`planner_store.day_tasks`, `or_(due_on, scheduled_on, start_on)`) would show it as a calendar
task, and `planner_day.slot_on_day` rewrites its `source_path`/`position` on first scheduling. So the date label is its own
nullable `label_date DATE`. Test: a date label leaves `scheduled_on`/`due_on`/`start_on` NULL.

## Schema (revision `f1a3c5e7b9d2`, after `d4f6a8c0e2b9`)

DDL only. `planner_tasks` gains `goal_ref VARCHAR(16)`, `label_month VARCHAR(7)`, `label_date DATE`, all NULL. On Postgres,
`CHECK (label_month ~ '^[0-9]{4}-(0[1-9]|1[0-2])$')` (`ck_planner_tasks_label_month`); SQLite has no regex operator, so the
API (pydantic pattern + service check) is the guard there. Verified on Postgres 17: full chain up, old-style INSERT still
works, 12 bad values rejected, down, up. The downgrade drops the three columns (and the CHECK).

## API (additive)

- `GET /vault/pipelines`: each item gains `goal_ref`, `label_month`, `label_date`; each block gains `ended_goals`.
- `PUT /vault/pipeline/goal` `{stream, line, goal_ref}`: the id must be a goal line of that block **this quarter** (else 422), or null.
- `PUT /vault/pipeline/label` `{stream, line, month | day}`: at most one; none clears. A month sets legacy `checkpoint` to its
  3-letter name if the month is in the current quarter, else NULL; a day or none clears `checkpoint`.
- `PUT /vault/pipeline/reorder` `{stream, line, direction: up|down}`: swaps with the neighbour in the same block and lane
  (the existing `move` only appends to a lane).
- Old writers keep the label in step: `PUT /vault/pipeline/checkpoint`, a `#month` in a new item or a rename set/clear
  `label_month` (year = the current quarter's).
- Export `planning_rows` and import carry the three fields (docs/export-format.md). The OpenAPI contract snapshot is regenerated
  (additions only).
- All writes go through the ORM session, so the shadow item-tree hook runs as before.

### New quarter carries blocks

`ensure_quarter` still creates a bare quarter. `plan_v2.carry_streams` runs on the Plan reads (`/quarter`, `/pipelines`,
`/objectives`): when this quarter has no blocks and an earlier one has, it copies the latest earlier quarter's blocks (slug,
name, color, icon, slot, weekly, has_pipeline, in_note, status, position) with empty goals and checkpoints. Idempotent; the
insert runs in a savepoint, so a concurrent request that loses the unique `(user, quarter, slug)` race just reads the winner's
rows. Items stay attached to the slug, so they appear under the carried block.

## CLI: `python -m app.cli plan-v2-migrate`

`--user N | --all`, dry run unless `--apply`. Prints one line per change (`id`, stream, what, before -> after), `TOTAL n changes`
and a machine-readable last line:

    SUMMARY label_month=<n> created=<n> created_next=<n> created_done=<n> matched=<n> ambiguous=<n> goal_ref=<n> overridden=<n>

(`label_month` = existing items whose label the run sets; `created` = new tasks; `goal_ref` = all items whose `goal_ref` it sets.)
Steps, in order, one transaction per user:

1. **label_month** from `checkpoint` for lane items with none. Year = the year of the stored quarter (Quarter/QuarterStream
   rows) the month falls in; zero or several candidate years -> `ambiguous`, skipped, printed. Items whose label month and
   checkpoint disagree are printed as `drift`, not changed.
2. **Checkpoint lines -> tasks**. Each month-checklist line of each block in each quarter: a task in the same block, lane `done`
   if ticked else `next` (appended to the block's order), `label_month` = that month, `origin = cpl:<quarter>:<mon>:<line id>`;
   skipped if that origin exists. A line matches a lane item of the same block (text normalised: lowercase, non-alphanumerics
   collapsed; equal, or one contains the other and the shorter is longer than 6) -> no task, `label_month` set if NULL, printed
   as `matched` with both texts and both months. **Only items that existed before the run are candidates**: two monthly lines
   with the same text become two tasks. Created tasks carry no `checkpoint` (the label is the new source of truth).
3. **goal_ref** for each block whose current-quarter goals are exactly one line, on every lane item of the block with none
   (including tasks created in step 2).

`--overrides file.json` = `{"match": {"<line id>": <item id>}, "skip": ["<line id>"]}`. `match` acts like a text match
(`matched (override)`), the item must exist, have a lane and be in the line's block, else the command aborts before any write;
`skip` creates nothing. Line ids come from the checklists; one id shared by several months (same text) applies to all of them.
Overrides are per user (not with `--all`).

Never deletes or edits checkpoint text/checklists, goal lines, week objectives or `focus_week`. A second run prints `TOTAL 0
changes`.

**Journal**: `--apply` writes `plan-v2-migrate-<user>-<UTC time>.json` (or `--journal PATH`) before committing (removed if the
commit fails): created rows and every `(id, column, old, new)` update, plus the overrides used.
**Revert**: `--revert journal.json` (dry run unless `--apply`). Deletes exactly the created tasks and restores old values, each
only if the row still equals what the run left; anything edited since is skipped and printed.

## Web

`apps/web/src/components/planner/plan-table.tsx` (rules in `src/lib/plan-v2.ts`, unit-tested). Columns Block (goals with
done/nested count, click = focus mode, `+ Q4'26 goal`, `Now n/3` warning), Now (`this week · W46`, "since W45"), Next
(`prioritized`, numbered per block, up/down), Someday. Cells group tasks under `↳ goal`, then `not nested`; Next shows 6 and
Someday 3 with `+n more`. Filters: Label (All, each month of the quarter, No label, Late n) and Block. `Done n` switches to a
Done table (Item, Block, Goal, Label; the checkbox reopens). The side card is the old item card with Status chips, a Goal
picker and a Label picker (months of the quarter, none, or a date). Notebook entries (ideas, meetings, blockers) show in
Someday. CompassBand, AdvisorPanel, PlanHeader (eyebrow `Plan · Q4'26`, `W46 · Nov-2026`), the capture bar and Habits stay.
Removed: PlanMap, WorkSection, MonthTrack, SmallDomino, StreamChip and the Month tab / carried-over chip (the Now column's
"since" replaces them).

## Rollback

- Web/API: redeploy the previous image. The three columns are ignored by it; nothing else changed in existing tables.
- Data: `plan-v2-migrate --revert <journal> --apply`. The schema revision can stay (nullable columns) or be downgraded after.
- If production runs the old core again and the owner edits checkpoints there, `label_month` can go stale. The CLI's step 1
  reports (does not fix) items whose label month disagrees with their checkpoint (`drift`); decide per item.
